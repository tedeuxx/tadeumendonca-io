## Finding 1 — A green can come from another checkout or another preview

what I saw · PR #727's marker records that the first Vitest invocation rooted itself in the main checkout and reported 170 green tests against code other than the reviewed head; only an explicit `--root` tested the worktree. PR #743's marker records the same failure class at the browser boundary: port 4173 was held by another worktree, `reuseExistingServer` silently reused that preview, and the first mutated E2E run exercised the other build. These are two independent observations in one iteration, so “the command passed” did not establish “this head passed.” · what it costs · A reviewer can publish a false green for the exact diff being attested, while the output looks normal. The serial review gate does not protect against a process from another worktree. · the change I propose, or the price of leaving it · Make repository test entrypoints bind themselves to the invoking worktree and fail closed on identity: Vitest receives the worktree's explicit root; browser suites allocate an isolated port and assert a head-specific build identifier or artifact path before tests run. Calibrate by starting a preview from a second worktree and proving the reviewed command refuses it, then restore and prove green. If left as instructions, every reviewer must remember both flags and the price is another plausible green against the wrong code.

## Finding 2 — The sprint-review origin survived in source but did not reach Codex runtime

what I saw · Issue #715 explicitly identified that the sprint-review browser bound came from the plugin's `.mcp.json`. PR #727 deliberately retained `HARNESS_SWEEP_ORIGIN` because the installed method consumes it, and its marker accepted that choice. At this closing rite, the Codex browser remained bound to the fail-closed `http://127.0.0.1:9/*`; sprint-review returned `SWEEP-ORIGIN-UNBOUND` and produced no `docs/iteration-sweep/sprint-06.md`. This is runtime evidence of absence, not evidence that the tracked setting or installed method is wrong. · what it costs · The reader-facing sweep is skipped on the harness used to close the sprint, so the retrospective receives no product observation and no report artifact. The failure is loud, but repeating the rite cannot repair a carrier that the active runtime did not load. · the change I propose, or the price of leaving it · Give each supported harness an explicit, inspectable carrier from the tracked origin to its browser allowlist, and have the session-start summary compare the configured value with the runtime value. Verification is a fresh Codex session whose native browser process shows the HTTPS allowlist and whose sprint-review writes the report. Do not infer or self-grant trust. If Codex cannot carry this setting, state that limitation in the rite and route the sweep to a harness that can, rather than presenting installation as runtime coverage.
